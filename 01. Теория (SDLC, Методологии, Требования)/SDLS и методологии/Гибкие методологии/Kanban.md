
# Kanban

## Что такое Kanban

**Kanban** — методология управления потоком работ, фокусирующаяся на **визуализации процесса**, **ограничении незавершённой работы (WIP)** и **непрерывном улучшении потока**. В отличие от Scrum, в Kanban **нет жёстких спринтов** — задачи берутся в работу по мере освобождения ёмкости.

> Если Scrum — это «спринтерский бег», то Kanban — это **«плавное течение реки»**, где задачи постоянно движутся от начала к концу.

Происходит из **Toyota Production System** (бережливое производство). Формализован Дэвидом Андерсоном в 2010 году.

---

## Шесть ключевых практик

| # | Практика | Суть |
|---|----------|------|
| 1 | **Визуализируй поток** | Канбан-доска с колонками |
| 2 | **Ограничь WIP** | Не бери больше, чем можешь завершить |
| 3 | **Управляй потоком** | Следи за метриками, убирай блокеры |
| 4 | **Явные политики** | Все правила записаны и понятны |
| 5 | **Петли обратной связи** | Регулярные встречи для улучшений |
| 6 | **Эволюционируй экспериментально** | Непрерывное улучшение (Kaizen) |

---

## Как это выглядит

### Канбан-доска
```
Backlog → Analysis → Ready for Dev → In Progress → Review → Testing → Done
```


### Пример

Заказчик просит починить баг на странице «Контакты»:

1. Задача падает в **Backlog**
2. Приоритизация: перемещаем в **Analysis** (SA прорабатывает)
3. Готово → **Ready for Dev**
4. Разработчик **вытягивает** задачу в **In Progress**
5. Готово → **Review** (код-ревью) → **Testing** → **Done**

В Kanban **нет дедлайна «конец спринта»**. Задача делается ровно столько, сколько нужно. Но благодаря WIP-лимитам команда не распыляется.

---

## Плюсы Kanban

- Плавный ритм без стресса спринтов
- Гибкость приоритизации в любой момент
- Фокус на завершении (Stop starting, start finishing)
- Прозрачность через метрики
- Минимум церемоний
- Идеален для поддержки и операционки

### Подходит, если:
- Непредсказуемый входящий поток (баги, инциденты, запросы)
- Нужна гибкость без стресса спринтов
- Команда устала от спринтов
- Нужно оптимизировать процесс (метрики показывают узкие места)

---

## Минусы Kanban

- Нет жёсткой предсказуемости релизов
- Требует высокой дисциплины (WIP легко нарушить)
- Меньше командного духа (нет общего ритма)
- Сложнее координировать большие фичи
- Риск «вечного потока» без видимых результатов

### Не подходит, если:
- Нужна жёсткая предсказуемость релизов → лучше Scrum
- Команда незрелая → без дисциплины доска превращается в свалку
- Нужен драйв и энергия спринта
- Сложные фичи требуют координации нескольких команд

# Kanban для системного аналитика

## Роль аналитика

В Kanban аналитик — это **хранитель потока и качества требований**. Главная задача: чтобы задачи не застревали на этапе анализа и плавно переходили в разработку.

> ⚠️ Главное правило: **Stop starting, start finishing**. Аналитик помогает доводить задачи до конца, а не плодит новые непроработанные тикеты.

## События (Cadences) и роль аналитика

В Kanban нет обязательных событий, но есть рекомендуемые ритмы:

| Событие | Частота | Роль аналитика |
|---------|---------|----------------|
| **Replenishment Meeting** | 1–2 раза/нед | 🔴 Ключевая. Решает, какие задачи из Backlog переместить в работу. Прорабатывает детали. |
| **Daily Stand-up** | Ежедневно, 15 мин | 🟠 Обсуждение блокеров. Помогает разблокировать задачи. |
| **Service Delivery Review** | 1–2 раза/нед | 🟡 Анализ метрик потока. Поиск причин задержек. |
| **Risk Meeting** | Еженедельно | 🟢 Обсуждение рисков и зависимостей. |
| **Operations Review** | Раз в месяц | 🟢 Стратегическое улучшение процесса. |

---

## Канбан-доска: колонки и роль SA

```
Backlog → Analysis → Ready for Dev → In Progress → Code Review → Testing → UAT → Done
```


| Колонка | Что делает SA |
|---------|---------------|
| **Backlog** | Грубая проработка, приоритизация с PO |
| **Analysis** | 🔴 Основная работа: детальные требования, AC, схемы, API |
| **Ready for Dev** | ✅ Задача готова, вся информация для разработчика |
| **In Progress** | 🟡 Ответы на вопросы, уточнение edge cases |
| **Testing** | 🟡 Помощь QA, разбор багов требований |
| **UAT** | 🟢 Приёмка фичи, демо стейкхолдерам |

## Ключевые артефакты

### Class of Service (Класс обслуживания)

| Класс          | Суть                                       | Пример                    |
|:---------------|:-------------------------------------------|:--------------------------|
| **Standard**   | Обычная задача, приоритет по FIFO          | Новая фича                |
| **Fixed Date** | Жёсткий дедлайн, штраф за просрочку        | Отчётность для ЦБ         |
| **Expedite**   | Срочная, нарушает WIP, делается немедленно | Критический инцидент (P0) |
| **Intangible** | Несрочная, но важная в долгосрок           | Рефакторинг, техдолг      |

### WIP-лимиты

Над каждой колонкой — максимальное количество задач:

```
Analysis (WIP=5) | In Progress (WIP=3) | Testing (WIP=4)
```

Если лимит достигнут — новая задача **не берётся**, пока не завершится старая.

### SLA (Service Level Agreement)

Целевое время прохождения задачи через систему:

| Тип задачи | Целевой Lead Time |
|------------|-------------------|
| Standard | ≤ 10 рабочих дней |
| Fixed Date | К фиксированной дате |
| Expedite | ≤ 4 часов |
| Intangible | Без жёсткого срока |

## Метрики Kanban

| Метрика | Что измеряет | Зачем аналитику |
|---------|--------------|-----------------|
| **Lead Time** | От создания до завершения | Как долго бизнес ждёт фичу |
| **Cycle Time** | От начала работы до завершения | Эффективность команды |
| **Throughput** | Задач завершено за период | Прогноз производительности |
| **WIP** | Задач в работе | Выявление перегрузки |
| **CFD** | Визуализация потока по колонкам | Поиск узких мест |

### Cumulative Flow Diagram (CFD)

```
Кол-во задач
│
50 │████████████████████ Done
│████████████████ Testing
40 │██████████████ In Progress
│██████████ Ready for Dev
30 │████████ Analysis
│████ Backlog
20 │
│
0 └────────────────────────── Время
```

**Что искать:**
- **Расширение** полосы → задачи накапливаются, есть bottleneck
- **Сужение** → поток улучшается
- **Плоская линия** → работа остановилась

**Пример:** полоса `Analysis` расширяется → аналитики не справляются → нужно оптимизировать или увеличить ресурсы.

## Определение готовности (DoR для Kanban)

```markdown
- [ ] Задача декомпозирована (влезает в 1–3 дня работы)
- [ ] Написаны Acceptance Criteria
- [ ] Есть макеты (если нужен UI)
- [ ] Описаны API-контракты и изменения БД
- [ ] Учтены нефункциональные требования
- [ ] Проведена встреча Three Amigos
- [ ] Определён Class of Service
- [ ] WIP-лимит на Analysis не нарушен
```

## Техники работы с требованиями

1. **Just-In-Time Analysis**
- Прорабатывать задачи тогда, когда они скоро понадобятся
- В колонке Analysis — задач на 1–2 недели вперёд, не больше
- Не тратить время на задачи, которые могут не войти в работу


2. **Explicit Policies (Явные политики)**
- Все правила записаны:
```
«Задача может находиться в Analysis не более 5 рабочих дней. Если дольше — эскалировать на Risk Meeting.»

«Expedite-задачи нарушают WIP. Одновременно может быть только 1 Expedite. После завершения — обязателен Root Cause Analysis.»
```

3. **Pull-система (Вытягивание)**
```
Задачи не назначаются сверху. Разработчик сам вытягивает следующую задачу, когда освободился
Аналитик обеспечивает, чтобы в Ready for Dev всегда были проработанные задачи.
```

## Управление потоком

```
Входящий запрос
↓
Быстрая оценка: Expedite или Standard?
↓
Expedite → немедленно в Analysis (нарушаем WIP)
Standard → в Backlog → ждём Replenishment
↓
На Replenishment:
  • SA представляет задачу
  • Обсуждаем приоритет с PO
  • Берём → перемещаем в Analysis
↓
SA прорабатывает (с учётом WIP-лимита)
↓
Готово → Ready for Dev
↓
Разработчик вытягивает, когда освободился
```

## Работа с блокерами

| Блокер                            | Действие                                   |
|:----------------------------------|:-------------------------------------------|
| Ждём ответ стейкхолдера > 2 дней  | Эскалация на Risk Meeting                  |
| Неясны требования смежной системы | Совместный созвон с аналитиком той системы |
| Нужна встреча с архитектором      | Бронируем слот, фиксируем на доске         |

## Плюсы и минусы для аналитика

### ✅ Плюсы
- Плавный ритм без авралов спринтов
- Гибкость приоритизации каждый день
- Прозрачность через метрики
- Минимум церемоний
- Фокус на завершении

### ❌ Минусы
- Риск «вечного анализа» без дедлайнов
- Сложность прогнозирования для бизнеса
- Требует высокой дисциплины
- Меньше командного духа
- Сложнее координировать большие фичи
