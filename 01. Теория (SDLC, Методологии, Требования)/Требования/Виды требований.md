## Контекст: Почему это важно

Представь, что заказчик говорит: *"Хочу, чтобы клиенты могли оплачивать заказы картой"*.

Как аналитик, ты должна **распаковать** эту фразу на несколько уровней требований. Каждый уровень отвечает на свой вопрос:
```
ЗАЧЕМ? → ЧТО? → КАК? Бизнес → Пользователь → Система
```


### 5 уровней требований (Пирамида требований)

#### 1️⃣ Бизнес-требования (Business Requirements)
**Вопрос:** *ЗАЧЕМ это бизнесу?*

Это верхний уровень — стратегические цели компании. Обычно формулируются через метрики и KPI.

**Примеры:**
- "Увеличить конверсию в покупку на 15% за Q1 2027"
- "Снизить нагрузку на колл-центр на 30% за счет автоматизации"
- "Выручка от онлайн-продаж должна составлять 40% от общей выручки"

**Кто формулирует:** Product Owner, руководство, бизнес-заказчик  
**Где фиксируется:** BRD (Business Requirements Document), стратегия продукта

---

#### 2️⃣ Пользовательские требования (User Requirements)
**Вопрос:** *ЧТО нужно пользователю для достижения его цели?*

Это потребности конечных пользователей, описанные на их языке (без технических деталей).

**Примеры:**
- "Покупатель хочет быстро найти нужный товар"
- "Курьер должен видеть оптимальный маршрут доставки"
- "Администратор хочет видеть статистику продаж за день"

**Кто формулирует:** BA или SA на основе интервью с пользователями  
**Где фиксируется:** User Stories, Use Cases, CJM (Customer Journey Map)

---

#### 3️⃣ Функциональные требования (Functional Requirements, FR)
**Вопрос:** *ЧТО должна делать система?*

Это конкретные функции, которые система должна выполнять. Формулируются через "Система должна..."

**Примеры:**
- "Система должна позволять пользователю добавлять товары в корзину"
- "Система должна отправлять email-уведомление после оформления заказа"
- "Система должна валидировать email при регистрации"

**Кто формулирует:** SA  
**Где фиксируется:** SRS (Software Requirements Specification), User Stories с Acceptance Criteria

---

#### 4️⃣ Нефункциональные требования (Non-Functional Requirements, NFR)
**Вопрос:** *КАК система должна работать?*

Это качественные характеристики системы: производительность, безопасность, доступность, масштабируемость.

**Категории NFR:**
- **Производительность:** время отклика, пропускная способность
- **Безопасность:** шифрование, авторизация, соответствие ФЗ-152
- **Доступность:** uptime (99.9%), время восстановления
- **Масштабируемость:** горизонтальное/вертикальное масштабирование
- **Надежность:** MTBF (Mean Time Between Failures)
- **Удобство использования:** время обучения, количество кликов

**Примеры:**
- "Время отклика API при добавлении товара в корзину не должно превышать 200 мс при нагрузке 1000 RPS"
- "Система должна быть доступна 99.9% времени (допускается 8.7 часов простоя в год)"
- "Пароли должны храниться только в хэшированном виде (bcrypt, минимум 10 раундов)"

**Кто формулирует:** SA совместно с архитектором  
**Где фиксируется:** SRS (раздел NFR), архитектурные решения

---

#### 5️⃣ Системные требования (System Requirements)
**Вопрос:** *В какой среде будет работать система?*

Технические ограничения и зависимости.

**Примеры:**
- "Серверная часть должна работать на Linux Ubuntu 22.04 LTS"
- "База данных — PostgreSQL 15+"
- "Клиентская часть должна поддерживать Chrome 90+, Firefox 88+, Safari 14+"
- "Интеграция с платежным шлюзом через REST API v2.1"

**Кто формулирует:** SA совместно с архитектором и DevOps  
**Где фиксируется:** SDS (System Design Specification)
